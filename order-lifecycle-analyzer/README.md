# order-lifecycle-analyzer

> **All data is synthetic or public. No employer or client data is used.** The order events analysed here are generated by a script in this repo.

Spans Penn Engineering courses **C1–C4**: Introduction to Python, Data Analysis Using Python, Introduction to Java & OOP, and Inheritance & Data Structures in Java.

## Problem

An order goes through a lifecycle: it is created (`new`), possibly modified (`replace`), and ends either filled (`fill`) or cancelled (`cancel`). Given a stream of those events, answer the operational questions a product or trading-ops team actually asks:

- What fraction of orders fill?
- How long does a fill take (p50 / p90 / p99 latency from `new` to `fill`)?
- What is the cancel-to-fill ratio, overall and by segment (venue, order size, time of day)?

## Two implementations

### Python (`python/`) — analytics
- Ingests a CSV of synthetic order events (`order_id, ts, event_type, qty, price, venue, ...`).
- Reconstructs each order's lifecycle with **pandas**.
- Computes fill rate, latency percentiles, and cancel-to-fill ratio.
- Charts the results with **matplotlib** (latency distribution, fill rate by segment).

### Java (`java/`) — event-matching core
Reimplements the lifecycle-matching logic as a class hierarchy:

```
OrderEvent (abstract)
├── NewOrder
├── Replace
├── Cancel
└── Fill
```

- An `OrderBook` index backed by a **`HashMap<String, Order>`** for O(1) lookup by order id.
- Each event type applies itself to the order state (polymorphic `apply`).
- **JUnit** tests cover the happy path and the awkward cases: replace-after-partial-fill, cancel of an unknown id, out-of-order timestamps.

## Layout

```
order-lifecycle-analyzer/
├── python/           ingestion, metrics, plotting
├── java/             OrderEvent hierarchy, OrderBook, JUnit tests
├── data/             synthetic CSVs (git-ignored; regenerate with the generator script)
├── tests/            pytest suite for the Python side
└── requirements.txt
```
